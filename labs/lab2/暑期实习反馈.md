## 二、遇到的问题

### 2.1 架构差异陡峭

SW64 与 RISC-V 在三个层面完全不同：
- **固件层**：OpenSBI → HMCODE，中断不走 `stvec` 而是 `wrent` 注册入口
- **指令层**：`la/tail/ecall` → `ldi/jmp/sys_call`，GP 寄存器必须显式初始化
- **地址层**：单一地址空间 → 四段地址空间，PADDR/KADDR 需识别双格式

每个 lab 都要重新理解一遍这套差异，比在熟悉架构上写代码慢很多。

### 2.2 HMCODE 黑盒困境

HMCODE 的接口（`wrent`、`wrkgp`、`wrtimer`、`rti`）清晰，但内部行为难以推测。lab1 的 HMCODE 保存区偏移量调了两天，最终靠对照 Linux `entry_c3.S` 源码才定位到 `old_sp - 0x30`。

### 2.3 调用约定的隐性约束

`call $31, trap` 的含义（`$31` 是零寄存器，表示不保存返回地址，`$26` 需手动设置为 `__trapret`）如果不看调用约定文档根本猜不到。

### 2.4 管道测试不可靠

SSH + echo + QEMU monitor 的 stdin 存在竞态，自动化测试经常失败。最终改为手动 `make qemu` + `pmemsave`。

## 三、收获

### 3.1 跨架构移植的系统性认知

不是逐行翻译代码，而是从固件/ABI/指令集/地址空间四个层面的差异出发，在源头修改。这个认知是三个 lab 反复踩坑后建立的。

### 3.2 SW64 中断机制完整理解

中断注册（wrent/wrkgp）→ HMCODE 触发（读 CSR → 保存上下文 → 跳转）→ 内核处理（SAVE_ALL/trap/do_entInt）→ 返回（RESTORE_ALL/rti）。现在不看文档也能画出完整流程。

### 3.3 物理内存管理的实践

`page_init` 中的内存布局、PADDR/KADDR 的地址切换、First-Fit 与 Best-Fit 的算法差异——从文档到代码再到 QEMU 输出，形成闭环。

### 3.4 调试方法论

分步隔离法：从最小功能（cprintf only）开始，逐步添加模块，每步编译运行验证。这种方法在不知道哪里出问题时特别有效。

### 3.5 工具链熟悉

`sw_64sw6b-sunway-linux-gnu-gcc/ld/objdump`、QEMU monitor、git 分支管理、Makefile 调试。
